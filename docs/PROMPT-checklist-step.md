# Повторяемый промпт для Cursor — чек-лист правок

Копируй блок **«ПРОМПТ LOOP»** для автоматического прогона или **«ПРОМПТ»** для ручного запуска.

---

## Запуск через Loop (каждые 30 минут)

Один раз в чате Cursor:

```
/loop 30m Реализуй следующий блок чек-листа Ibra Cargo Pay. Источники и workflow: docs/PROMPT-checklist-step.md (раздел «ПРОМПТ LOOP»). БЛОК: auto
```

**Поведение loop:**
- Каждые 30 минут агент читает `docs/PLAN-progress.md` и сам выбирает режим (см. ниже).
- Если предыдущий блок не ✅ — **не переходит** к следующему, чинит текущий.
- Если все 12 блоков ✅ — переключается на **режим аудита** (код не менять).
- После каждого успешного блока (тесты зелёные) — **обязательный git commit** (см. шаг 9).
- Если тесты красные после 3 итераций — остановись до следующего tick; блокер пиши в журнал прогресса.

**Остановить loop:** напиши «останови loop чек-листа».

---

## Режимы работы (определяются автоматически)

| Условие | Режим | Действие |
|---------|-------|----------|
| В `PLAN-progress.md` есть блок без ✅ | **Реализация** | Шаги 1–10 workflow |
| Все 12 блоков ✅ | **Аудит** | Шаги A1–A6 (read-only) |

Файл аудита (только дописывать, не перезаписывать историю): **`docs/AUDIT-checklist-review.md`**

## 0. ВЫБОР РЕЖИМА

1. Открой docs/PLAN-progress.md.
2. Если **все 12 блоков** имеют статус ✅ → перейди в **РЕЖИМ АУДИТА** (раздел «Аудит» ниже), workflow реализации НЕ выполняй.
3. Иначе → **РЕЖИМ РЕАЛИЗАЦИИ** (шаги 1–10).

---

## РЕЖИМ РЕАЛИЗАЦИИ

### 1. Проверка предыдущего блока
- Если это не Блок 1: предыдущий блок должен быть ✅ с зелёными тестами в журнале.
- Если нет — не начинай новый блок; почини предыдущий или текущий незавершённый.
- В ответе: «Предыдущий блок: [N] — [✅/❌/—]».

### 2. Определи задачу
- При БЛОК: auto — первый блок без ✅ в PLAN-progress.md.
- Перечисли шаги из PLAN-checklist-pravok.md.
- Напиши: «Выполняю: Блок N, шаги X.Y–X.Z».

### 3. Реализация
- Только шаги текущего блока, минимальный diff.
- Бизнес-правила из плана (shared_access, client_id, платежи без approval, effective_cost_price).
- Ветка: feature/checklist-pravok (создай от main если нет).

### 4. Тесты
- Backend: pytest + httpx (FastAPI). Если pytest ещё нет — настрой в этом блоке.
- Тесты на поведение из раздела «Итог» шагов, не тавтологии.
- Файлы: backend/tests/test_*.py
- Frontend (если блок затрагивает): vitest для утилит; для UI — tsc --noEmit.

### 5. Запуск
- Backend: cd backend && python -m pytest tests/ -v --tb=short
- Frontend (если менялся): cd frontend && npm run lint
- Миграции (если есть): cd backend && alembic upgrade head

### 6. Цикл исправлений
- Падает → исправь → перезапусти (до 3 раз).
- Закрывать блок можно только если:
  • все тесты зелёные;
  • lint/tsc без ошибок в изменённых файлах;
  • ≥1 тест на каждый новый endpoint / ключевое правило доступа.
- После 3 неудач — статус блока 🔄 или ❌ в PLAN-progress, блокер в журнал; **коммит не делать**.

### 7. Отметка прогресса
- docs/PLAN-progress.md: статус ✅, дата, результат тестов, журнал.
- docs/PLAN-checklist-pravok.md: у каждого шага блока строка:
  > ✅ Выполнено | Тесты: N/N | Дата: YYYY-MM-DD

### 8. Git commit (ОБЯЗАТЕЛЕН при ✅ блока и зелёных тестах)

Выполняй **только** если блок закрыт ✅ и все тесты/lint прошли.

1. Параллельно: git status, git diff, git log -5 --oneline.
2. Не коммить .env, credentials и прочие секреты.
3. git add только файлы, относящиеся к блоку (+ docs/PLAN-progress.md, docs/PLAN-checklist-pravok.md).
4. Сообщение коммита (HEREDOC), формат:

   feat(checklist): блок N — краткое описание (шаги X.Y–X.Z)

   - что сделано (2–4 пункта)
   - тесты: N passed

   Примеры:
   - feat(checklist): блок 1 — фаза 0, ветка и permissions.py (шаги 0.1–0.3)
   - feat(checklist): блок 2 — раздел 1 backend CRUD и права (шаги 1.1–1.7)

5. git commit, затем git status — убедись что commit прошёл.
6. **Не push** без явной просьбы пользователя.

### 9. Итоговый отчёт в чате
1. Предыдущий блок — проверка
2. Текущий блок — что сделано
3. Изменённые файлы
4. Тесты — команда и N passed / failed
5. Git — hash коммита или «коммит пропущен (причина)»
6. Прогресс — X/12 блоков ✅
7. Следующий блок — что делать дальше

## РЕЖИМ АУДИТА (все 12 блоков ✅)

**Строго read-only:** не редактировать код, конфиги, миграции, package.json.
Разрешено **только** дописывать docs/AUDIT-checklist-review.md и журнал в PLAN-progress.md.

### A1. Определи фокус прогона
- Открой docs/AUDIT-checklist-review.md — найди последний прогон.
- Выбери **новую** область (не дублируй уже проверенное без причины):
  1. backend/app/core/permissions.py и использование прав
  2. backend routes (items, payments, payment_requests)
  3. frontend pages/components по разделам плана
  4. cross-cutting: shared_access, client_id, confirmed payments, cost_price NULL
  5. тесты: пробелы в пок покрытии vs «Итог» шагов
  6. security: auth, IDOR, upload paths
  7. финальный сводный прогон (если все области уже пройдены — повтор с другим углом)

### A2. Проверка (read-only)
- Читай код, grep, pytest --collect-only при необходимости.
- Сверяй с бизнес-правилами из PLAN-checklist-pravok.md (таблица в начале).
- Маркер регрессии: diff от 4ccfd2b при сомнениях.

### A3. Запись в docs/AUDIT-checklist-review.md

Добавь новую секцию в конец файла:

## Прогон YYYY-MM-DD HH:MM — [область]

**Режим:** read-only аудит (loop)
**Проверено:** [файлы/модули]

### Находки

| Severity | Файл | Описание | Рекомендация |
|----------|------|----------|--------------|
| critical/high/medium/low/info | path:line | что не так | что сделать (без правок сейчас) |

### Соответствие бизнес-правилам
- [ ] shared_access CRUD
- [ ] payment request edit/delete
- [ ] payment delete owner rule
- [ ] client_id не в API/UI
- [ ] cost NULL = price
- [ ] payments без approval (confirmed сразу)

### Итог прогона
Краткий вывод: N critical, N high, … Следующая область для следующего tick.

### A4. Тесты (только запуск, без правок)
- cd backend && python -m pytest tests/ -v --tb=short
- Если упали — **не чини код**; зафиксируй как critical finding в аудите.

### A5. Журнал
- В PLAN-progress.md в «Журнал прогонов» добавь строку: дата, «Аудит: [область]», результат pytest, ссылка на секцию в AUDIT.

### A6. Отчёт в чате
1. Режим: Аудит (read-only)
2. Область проверки
3. N находок по severity
4. Тесты: N passed / failed (без исправлений)
5. Следующая область для tick +30m

---
